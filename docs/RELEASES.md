# Releases: trust, verification and updates

This page describes how VibeSync is released **today** and what it would take to add code signing and automatic updates. Nothing here is aspirational: if a feature is listed under *Not set up yet*, it doesn't work yet.

## Current state

| | Status |
| --- | --- |
| Installer | `VibeSync-Setup-<version>.exe` (NSIS, per-user, built by electron-builder) attached to each [GitHub Release](https://github.com/dhirenv-21/vibesync/releases) |
| Code signing | **Not signed.** Windows SmartScreen shows *"Windows protected your PC"* on first run |
| Checksum | **SHA-256 published** in each release's notes |
| Automatic updates | **Not set up.** VibeSync never checks for or downloads updates |
| Build provenance | Built locally from the tagged commit; CI runs the tests on every push but doesn't build releases |

## Verifying a download

Because the installer is unsigned, the checksum is how you confirm the file is the one that was published.

1. Download `VibeSync-Setup-<version>.exe` from the [Releases page](https://github.com/dhirenv-21/vibesync/releases). Don't use mirrors or re-uploads.
2. In PowerShell, in the download folder:

   ```powershell
   Get-FileHash .\VibeSync-Setup-0.5.0.exe -Algorithm SHA256
   ```

3. Compare the `Hash` value with the **SHA-256** line in that release's notes (case doesn't matter). If they differ, don't run the file.

Then, when SmartScreen appears, choose **More info → Run anyway**. SmartScreen warns because the file has no publisher signature, not because anything was detected in it.

## Updating

There's no auto-update. To update:

1. Download the newer installer from the Releases page (and verify it as above).
2. Close VibeSync (including the screen glow) and run the installer. It installs over the existing version.
3. Your settings, display choices and cached lyrics live in `%APPDATA%\VibeSync` and are kept. (Upgrading from Glowline moves them there from `%APPDATA%\Glowline` on first launch.)

To get notified of new versions, use **Watch → Custom → Releases** on the GitHub repository.

## Not set up yet: code signing (next steps for maintainers)

Signing removes the "unknown publisher" warning over time and lets Windows show who published the file. Practical options:

1. **Pick a signing route.**
   - **SignPath Foundation:** free code signing for qualifying open-source projects; signing runs in their service from a CI artifact, so no certificate is stored in this repo.
   - **Azure Trusted Signing:** low-cost managed signing (requires identity validation); electron-builder 26 supports it via `win.azureSignOptions`.
   - **A traditional OV/EV Authenticode certificate** from a CA (DigiCert, Sectigo, …). EV certificates live on a hardware token or cloud HSM.
2. **Keep secrets out of git.** Never commit a `.pfx`, password or token. In GitHub Actions, store them as encrypted repository secrets (e.g. `WIN_CSC_LINK` / `WIN_CSC_KEY_PASSWORD` for a certificate file, or the Azure client credentials) and expose them only to a release job that runs on tags.
3. **Build releases in CI.** Add a `release.yml` workflow on `v*` tags that runs `npm ci`, `npm test`, `npm run dist`, signs, and attaches the installer plus its SHA-256 to the GitHub Release, so every published binary comes from a visible build.
4. **Verify after signing:** `Get-AuthenticodeSignature .\VibeSync-Setup-x.y.z.exe` should report `Valid` with the expected publisher.

## Not set up yet: automatic updates (next steps for maintainers)

Do this **after** signing is in place, so updates can't be swapped for unsigned files.

1. Add `electron-updater` and a `publish` block in `vibesync/package.json` (`"provider": "github", "owner": "dhirenv-21", "repo": "vibesync"`).
2. Publish `latest.yml` (generated by electron-builder next to the installer; it contains the installer's SHA-512) and the `.blockmap` with every release; electron-updater verifies the download against it.
3. In the main process, check for updates on launch at most once a day, **ask before downloading**, and install on quit. Add a Settings switch to turn checks off, and document that checks contact `github.com`.
4. Test the update path from the previous release to the new one before publishing.

Until then, the manual steps under [Updating](#updating) are the supported way to upgrade.
